1. 用原始用户目标重新建立验收基线
不要只检查最近 diff。先从最新本地应用的项目中心开始，分别以普通部门负责人、业务成员、只读成员走完整路径；管理员身份仅用于真正需要的平台管理。
审查：项目中心、创建与编辑、初始化、数据接入、数据集、指标、看板、实际业务页、报告、成员及项目设置。运行应用并捕获真实界面。保存前后对比、首次进入、关键中间步骤、失败恢复和已使用状态。
把发现分成：
- 阻断公司推广的主流程缺口；
- 影响上手与日常使用的整体体验缺口；
- 可在试点后修复的局部问题。
本轮主要投入前两类，不把进度报告再次变成计算边界反例清单。
重点复核以下产品结构线索：
- ProjectCenter 的客户是已有数据选择，缺少新客户进入和维护的完整路径；负责人字段虽有数据模型，创建和资料表单没有形成一致选择体验。
- general_workbench 模板默认安装任务、预算、负责人指标，不是适合任意部门表格的中性起点。
- OverviewWorkspace 仅 general_workbench 使用动态 GeneralWorkbenchBoard；内容营销、评论和投放仍有各自专用主体。这不是要求它们看起来一样，而是检查它们能否共用配置与来源绑定。
- 数据管理导航目前指向设置页 data-sources，数据集明细又在总览，数据地图另有指标与映射。用户需要理解过多重复概念。
- CardEditModal 把计算规则放在卡片中；DataMap 又维护指标定义。检查“统一指标”是否成为真实共享对象，而不只是同一个计算函数。
- 通用看板编辑仅提供单值、进度、分组列表，丰富趋势和分析图多在启萃专用页面；新部门无法通过界面获得相当的基本分析体验。
- 通用导入进入 datasets；投放主体取 dashboard.feishu.daily 等专用数据。必须验证新投放项目从导入到自身业务图表的真实链路。
- app/api/agent/route.ts 的取数与分析仍包含社媒/母婴业务假设，不能默认它已适用于所有部门报告。
- 表单、页面标题、分层导航、技术字段展示需要整体收敛，不能仅把原生 select 换成 CustomSelect。
至少维护 docs/product-integration-v1/brief.md、scope.md、acceptance.md 和 handoff.md，记录真实进度，不以文档代替开发。
2. 产品工作包一：统一入口与新项目首用体验
2.1 项目中心成为真正的客户/部门项目入口
沿用现有客户、部门、用户、项目模型，补最小可用界面，不做复杂 CRM。
项目中心支持按授权范围查看“我参与的”“我负责的”和全部可见项目，按客户、部门、负责人、状态筛选。项目卡片至少清楚呈现名称、客户或内部项目、部门、负责人、项目状态、数据更新时间和需要继续完成的设置。
项目多时提供紧凑列表视图；不得为了项目卡片美观而使十几个项目难以比较。来源尚未配置和当前周期没有记录应区分。
有权限的人能新增/维护客户和部门，或进入明确的现有组织管理入口。无权限的人能看到可执行的联系/申请路径。不能要求用户向开发人员申请修改种子或数据库。
2.2 创建与编辑共用项目表单
核心信息：名称、负责部门、负责人、客户/内部项目、说明。负责人默认为当前人但允许有权限者调整。
业务状态有合理默认，识别色自动分配并在次要设置中调整。品牌/SPU 是相关业务的扩展信息，不对无关项目必填或抢占主要位置。
新建、项目中心编辑、项目资料使用同一表单与字段规则。选择一种统一承载方式（抽屉、Dialog 或完整页面），避免新建插在列表上方、编辑另一套、设置又一套。
2.3 把五步技术清单整合成一条带结果的首用路径
推荐主路径：
创建基本资料 → 选择业务方向或空白项目 → 接入数据 → 确认推荐指标/看板 → 发布团队工作台。
成员添加可在合适时完成，不应阻止单人试用。已有初始化持久化和真实就绪校验继续有效。
首屏突出一个下一步操作。已完成步骤收起，首次设置结束后进入日常工作界面，不持续占据大面积向导。
不要让新用户同时理解“数据源、数据集、指标定义、卡片配置、数据地图、空值策略、版本发布”。提供合适默认和业务说明，需要时再展开高级设置。
2.4 模板是推荐与复用，不是新的强制业务结构
保留通用、内容营销、评论、投放方向；允许空白起步。通用模板不自动假定每张表都包含状态、预算、支出或 owner。
模板至少说明：适用场景、必要字段、可选字段、推荐指标与示例看板。读取真实字段后只推荐能够计算的内容，缺项明确说明，不生成大批无关错误卡。
模板不携带真实客户、凭证、来源链接、供应商、已完成数据或固定目标。启萃已确认的真实目标保留在启萃项目；新项目目标要求明确确认，不能默认继承200/60/300等数值。
新增项目可复制已授权项目的结构和指标模板，但复制前明确不复制来源授权、私有数据和真实目标。V1可先提供管理员维护的模板，不要求复杂模板市场。
验收：新建一个真实未登记过的客户/部门项目，不用改代码或DB；原表只有日期、渠道、咨询人数、成交人数，也能完成初始化并获得正确的第一份看板。
3. 产品工作包二：数据、指标、看板形成一套用户能理解的体系
3.1 整合数据工作台
项目内“数据”管理来源、数据集、字段与同步记录。不要仅把数据源设置的链接改名为数据管理。
数据页建议分为：数据源、数据集、同步记录。数据集详情提供来源、字段、预览/明细、质量问题及“创建指标/加入看板”。来源可直接看到其生成的数据集与使用它的指标。
保留现有链接识别、选表、样本预览、映射、完整批次校验、失败保护、分页和来源级更新。默认流程面向业务人员，高级栏承载主键、复杂空值/单位规则等，不隐藏必要校验。
清楚说明“飞书数据为准；在何处修改记录；多久更新；当前是否自动同步”。未启用调度必须真实标注。不要新增一套会和飞书互相覆盖的通用编辑系统。
3.2 指标成为可复用对象，而不是每张卡重复定义
优先利用现有 metric_definitions、metric_bindings 和计算服务，补齐它们与动态卡片的关系。
用户创建“成交率”时只定义一次来源、分子分母、时间字段、单位与缺失规则。指标卡、趋势图、分组图、报告引用同一指标标识及适用配置。
普通添加卡片流程应为：选指标 → 选呈现方式 → 保存。找不到指标时可“新建指标”，高级编辑仍然可用。
不同项目可绑定不同来源。共享标准指标与项目私有指标明确区分。不能把所有同名指标强制合并，不能跨项目比较不同口径而不提示。
一个指标变更后应展示影响范围；图表和报告依据明确版本计算。V1不要求复杂审批系统，但必须避免同名指标在卡片和报告各算各的。
DataMap可以保留给管理员/高级用户，普通用户不需要通过账户、endpoint、JSON等界面配置经营指标。
3.3 所有项目共用配置能力，模板可以有不同内容
建立同一看板配置入口与组件登记机制；通用项目不是唯一可以自定义的项目。
保留启萃复杂图表和原业务能力，将它们作为可登记、可按项目启用和配置的业务组件。无需把每种历史图表一次改成通用 BI 引擎，但不能继续只有改 JSX 才能调整启萃布局。
V1通用呈现至少包括：指标卡、时间趋势、分组对比、明细表、目标进度。复用现有图表组件，不建设无限画布。可采用有限尺寸、上下移动和区块布局，无需复杂拖拽。
支持项目级日期范围与常用筛选，卡片若独立覆盖范围必须标注。默认团队看板由有权成员发布；只读成员不应进入无法保存的配置流程。个人布局、任意联表、跨项目大 BI 可以后置。
关键验收：更改同一指标定义后，单值、趋势、分组和报告输出一致；不同客户的两个同类项目可用相同模板但不同数据源和目标。
3.4 打通来源到专用业务页，不以“入库成功”结束
分别追踪：飞书来源 → 映射/适配 → 项目数据 → 指标/业务对象 → 页面图表。
例如新投放项目导入“日期、渠道、花费、曝光、点击”，其投放总览必须使用这批数据。不能只有通用数据集有记录，专门的投放页面仍等待启萃历史汇总。
评论/内容模板也要说明需要什么来源、导入后进入什么业务对象、哪些功能需要额外外部接口。未具备的能力显式待配置，不能通过模板名称承诺已实现。
不把所有领域强行塞入通用表；保留业务适配器，但使用一致的项目归属、来源和指标契约。
4. 产品工作包三：从配置页面变为日常工作与成果输出
4.1 区分配置者、使用者和查看者
项目管理员负责接入、指标和团队看板。业务成员查看自己需要的信息并执行授权的既有业务操作。只读成员应直接看到清楚的结果，不被配置按钮和管理员术语打扰。
正常使用主页需要回答：目前怎样、相较上期怎样、哪里异常、接下来做什么、数据可信到哪一天。
使用现有任务/处置模块承接已有业务；非社媒部门可以跳回飞书原记录处理。不要为了“闭环”新造全公司的任务与审批体系。
4.2 报告和 AI 必须消费当前项目的同一指标
检查现有报告取数、系统提示与外部业务数据选择，清理默认社媒/母婴假设对其他项目的影响。
V1先完成可核对的项目报告：项目、周期、关键指标、趋势、异常、来源和更新时间，可查看历史版本及按权限导出。AI结论可以是可选增强，没有模型凭证时也能导出真实结果，不编造分析。
启萃报告保留专属内容模板；通用项目报告不得夹带飞鹤、启萃、母婴大盘或无关账户。不能仅在报告标题替换项目名。
从看板进入报告，默认继承项目和周期；输出与看板同口径。已有的 report_versions、保存报告和导出能力优先复用。
4.3 只保留推广必需的身份与授权底线
本轮不重造大型SSO，但不能把测试管理员回退、未验证请求头或任意令牌当成企业真实身份。
核查生产入口的身份信任边界：真实会话或受信网关注入、测试身份仅隔离环境可用、默认拒绝未知身份。保留服务端项目鉴权。
用两个普通成员和一个管理员验证：项目中心、数据、图表、报告、导出和AI只看有权内容；只读成员不会被引导去做必失败的写操作。
权限未通过时，只能使用隔离的合成/脱敏数据测试，不宣称可以承载跨部门真实客户数据。
5. 产品工作包四：统一 UI，不做一次新的表面换肤
先运行本地应用截取完整用户路径，再提出一致的信息结构并实施。不要拿旧报告或概念图当作当前完成后的截图。
5.1 统一页面框架
建议顶层为项目中心及授权的平台基础管理；项目内为：
概览/看板｜数据｜指标｜已启用业务模块｜报告｜设置。
这是信息分组目标，可结合现有布局适当收敛数量。不能出现多个同义入口分别配置互相不相连的指标，也不要求为每个名词都新增一级菜单。
统一项目上下文：客户、项目名、负责部门/负责人、业务状态。主操作、日期筛选与数据新鲜度放在一致位置。项目切换不带旧项目状态。
设置负责资料、成员、业务规则和生命周期，不继续承载所有高频数据操作。
5.2 页面分层，而不是把所有内容做成同等醒目的卡片
首页：简洁项目头部、少量核心指标、趋势/对比、异常或待办、来源状态。
详细分析进入对应业务页。密集配置进入编辑抽屉或独立页面。技术细节按需展开。
清楚区分数据值、状态、说明和下一步操作。颜色用于语义与少量项目识别，不把每块内容都变成高饱和彩色区块。
避免重复英文眉题、版本徽标、项目标题、说明卡反复占据首屏。面向业务人员改写“数据边界、语义层、来源级落库、已解锁能力”等文案。
5.3 统一表单和常见状态
复用已有Dialog、CustomSelect、反馈、EmptyState和图表组件，统一字号、间距、表单高度、按钮优先级、弹窗动作区、错误位置和空状态。
新建与编辑的状态/识别色采用同一组件，识别色不是创建流程的视觉主角。
首用、加载、空数据、来源缺失、未配置、无权限、失败、过期和未保存，形成统一处理方式。空状态给正确角色一个可执行操作。
验证1280/1440桌面，另检查768/390窄屏。移动端不是主设计目标，但核心操作不能溢出或不可访问。打开下拉、映射、编辑和确认框检查，而不是仅截图首页。
6. 改变验收方式：使用真实业务场景而非满足模板的测试夹具
已有自动化回归继续运行，用于防止正确性退化。本轮新增的是整体产品验收，不靠增加方法级用例数量宣布推广就绪。
场景一：完全陌生的非社媒部门。
原表只含日期、渠道、咨询人数、成交人数，没有status/budget/spent/owner。新建部门/客户或内部项目，经页面接入并确认推荐看板，查看趋势和渠道对比，添加只读成员，输出同口径报告。不得先给来源补上模板喜欢的字段。
场景二：第二个客户的投放项目。
使用新的文档、新的客户、新的账户或映射；原表含日期、渠道、花费、曝光、点击。导入后专属投放页真实变化，配置自己的图表和目标，不借用启萃来源或数据。不配置真实广告账户时，可验证授权飞书投放表路径并准确标明来源。
场景三：既有启萃。
旧数据、复杂图表、业务操作和报告继续有效；能调整团队看板布局与组件选择；原业务规则和目标保留在启萃实例，不复制到其他客户。不能以删减旧业务换通用化成功。
场景四：角色与返回使用。
负责人创建并发布；第二位成员首次进入；只读成员查看报告；管理员调整后成员刷新获取更新。用真实角色测试，不让全流程都借平台管理员通行。
每个场景记录：是否独立完成、在哪一步需要解释或开发介入、首次看到有效结果的实际时间、关键操作数、迷路返回次数、数据对账与报告一致性。
这些度量是产品对比与阻塞定位工具，不编造时间，不将某个没有实测的分钟数当宣传承诺。真实用户访谈或部门试用未进行时明确“未进行”，不要让自动化脚本冒充真人体验结果。
测试环境可模拟外部飞书接口，但本地转换、存储、计算、配置、渲染和报告必须真实执行。真实飞书联调与生产授权需要单独验收，不能用模拟服务结果替代。
7. 开发顺序与完成标志
按用户路径做纵向交付，不按新增数据库表数量交付：
第一批：项目中心、客户/负责人、新建表单、轻量首用与统一页面框架。

完成标志：没有阻断核心路径的问题，真实环境未验部分明确列出。普通局部优化进入试点清单，不再次扩成无止境重构。

8. 最终交付格式
1. 对原始需求逐项回答：多客户入口、新项目接入、项目差异、统一指标、权限、统一UI、启萃保留分别达到什么状态。
2. 给出四条完整产品路径的结果与实际证据，不只给API/单元通过数。
3. 提供关键页面改造前后截图；截图须实际打开检查，标明项目、角色、页面状态和环境。
4. 说明哪些旧能力复用、哪些页面合并、哪些新模块确有必要。
5. 分开列出静态检查、单元/API、浏览器、真人试用、真实飞书和生产验证。
6. 提供起始/最终SHA、分支、提交/推送/合并/部署状态和工作区状态。
7. 列出推广阻断、试点后优化和暂不建设三类剩余事项，不写无边界的“全部100%”。
最终标准不是“又修了一轮bug”或“所有卡片都能保存”，而是：
一个新部门不需要理解系统内部实现，也不需要开发人员替它配置，就能创建自己的项目，接入自己的表，得到自己的指标、图表和报告，让正确的人协作；启萃作为其中一个项目继续完整可用。
